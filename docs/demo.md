# Demonstration guide

> **Status: skeleton.** The demonstration scenarios (D01–D06) are built in Phases 3–5.
> This file currently covers only what exists after Phase 1: starting the stack and
> signing five laptops into five consoles. It is filled in as the scenarios land, and
> nothing is described here as working before it has been run.

---

## Accounts

Five accounts, one per console. Passwords are generated by
`scripts/seed_users.py` and printed once when it runs — they are not stored in this
repository, and the table below deliberately leaves the column blank.

| Laptop | Username | Console | Role |
|---|---|---|---|
| 1 | `simulator` | `/simulator/` | Run control and condition injection |
| 2 | `master` | `/master/` | All incidents, forecasts, recovery approval |
| 3 | `power` | `/power/` | Generation, battery, electrical load |
| 4 | `thermal` | `/thermal/` | Temperatures, heaters, propellant, pressure |
| 5 | `flight` | `/flight/` | Attitude, wheel, link, computer health |

A single shared login page routes each account to its own console. There is no role
selector: the server decides from the authenticated account.

## Starting the stack

```bash
cd frontend && npm run build          # produces frontend/out for Caddy
cd .. && docker compose up -d --build
```

Then open the site at `SITE_ADDRESS` from `.env` (`http://localhost:8080` by default).

Check before the audience arrives:

1. `docker compose ps` — `db`, `api` and `caddy` all up.
2. Sign in on each of the five consoles and confirm each lands on its own route.
3. Refresh a console directly by URL (e.g. `/master/`) to confirm the reverse proxy
   serves it without a 404.

## Reset and stop

```bash
docker compose restart api     # backend restart; the run comes back PAUSED
docker compose down            # stop everything, keeping the database volume
```

Never use `docker compose down -v` during a demo: `-v` deletes the `ps01_pgdata` volume
and with it every stored run.
