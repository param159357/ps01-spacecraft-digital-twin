# Demonstration guide

Five laptops, one deployed site, one authoritative backend run. Every number quoted here
was observed on a real run; where a value drifts slightly between runs the text says so.
This is a fictional demonstration vehicle — no part of it is a validated spacecraft model.

---

## Accounts

Five accounts, one per console. Passwords are generated by `scripts/seed_users.py` and
printed once when it runs. They are not stored in this repository, which is why the table
below leaves the column blank.

| Laptop | Username | Console | Role |
|---|---|---|---|
| 1 | `simulator` | `/simulator/` | Run control and condition injection |
| 2 | `master` | `/master/` | All incidents, forecasts, recovery approval |
| 3 | `power` | `/power/` | Generation, battery, electrical load |
| 4 | `thermal` | `/thermal/` | Temperatures, heaters, propellant, pressure |
| 5 | `flight` | `/flight/` | Attitude, wheel, link, computer health |

One shared login page routes each account to its own console. There is no role selector:
the server decides from the authenticated account. A specialist who types another
console's URL is sent back to its own.

**Before the audience arrives**, rotate the passwords: `python scripts/seed_users.py
--reset-passwords`. Any password that has been pasted into a chat window or a terminal
someone has seen should be treated as spent.

## Starting the stack

```bash
cd frontend && npm run build
```

```bash
docker compose up -d --build
```

Caddy serves `frontend/out` and proxies `/api` to the API container, including SSE, so the
browser sees one origin. Open the site at `SITE_ADDRESS` from `.env` — `http://localhost:8080`
by default.

`APP_ORIGIN` in `.env` **must** match the address the browser actually uses. If it does
not, sign-in fails with a 403 and nothing else works; that is the single most common way
to lose ten minutes before a demo.

Pre-flight, in order:

1. `docker compose ps` — `db`, `api` and `caddy` all up, `db` healthy.
2. Sign in on each of the five laptops; confirm each lands on its own console.
3. Refresh one console directly by URL (e.g. `/master/`) — it must render, not 404.
4. On the simulator console press **Start** and confirm the spacecraft clock advances on
   all five screens at once.
5. Check the header on every laptop reads **CONNECTED** with a data age under ~2 s.

## The demonstration

Run D02 first. It is the complete loop and the one to show if there is only time for one.

### D01 — normal sunlight and eclipse (about 1 minute)

**Simulator:** press **Load D01 eclipse transition**. This resets to 70% state of charge
ten simulated seconds before a scheduled eclipse, and starts the run.

**What to point at:** the header illumination flips `SUNLIGHT` → `ECLIPSE`, generation
falls to zero, the battery begins discharging, and **no incident opens**. A scheduled
eclipse is expected behaviour, not a generation fault — that distinction is the point of
the scenario.

### D02 — recoverable extra load before eclipse (about 3 minutes)

**Simulator:** press **Load D02 recovery demo**. Labelled starting condition: 24% observed
state of charge with a 200 W unexplained load, payload at 100%.

1. **All consoles** — requested load sits near 380 W; the power console shows the battery
   discharging.
2. **Master** — within about a minute an `ENERGY_RESERVE` `WARNING` opens. The same
   incident ID appears on the power console under "Power scope".
3. **Master** — press **Compare payload reduction**. On a verified run the no-action
   baseline crossed the 20% reserve at about +690 s and the 10% critical reserve at about
   +1590 s; with the payload reduced the warning crossing moved out to about +870 s and
   **no critical crossing occurred inside the 30-minute horizon**. The panel states its
   assumptions and the mission trade-off.
4. **Master** — approve. Press twice if you like: the second press returns the same
   command record. The proposal expires after 30 s; if you leave it on screen and then
   approve, you get an honest `409` and compare again.
5. **Master and power** — measured `load_power` falls. On the verified run it went
   **379.7 → 300.2 W** and the command reported `APPLIED` then outcome **IMPROVED**.

The sentence worth saying out loud: *accepted is not applied, and applied is not
recovered.* The outcome is decided from later measurements, not from the approval.

### D03 — the same problem ignored (about 4 minutes, mostly waiting)

**Simulator:** press **Load D03 delayed response**. Labelled starting condition: 11% state
of charge shortly before a scheduled eclipse, with a 300 W unexplained load.

Take no action. The `ENERGY_RESERVE` incident escalates `WARNING` → `CRITICAL`. Carried to
its conclusion the battery empties, the declared load shedding drops the payload, and the
master console reports **payload operation lost** in seconds — a counter that only ever
increases.

Then recover. The payload comes back; the lost-time counter does not go down. On the
verified run 6 s of payload operation were lost and were still lost 18 s after full
recovery.

**Do not claim battery damage.** This model has none, and a drained battery recharges
normally. The irreversible consequence here is lost operating time.

### D04 — stuck-on optional branch (about 3 minutes)

**Simulator:** press **Load D04 stuck branch**. Labelled starting condition: 28% state of
charge, payload node starting at 53 °C, with the optional branch stuck energised.

1. **Thermal** — `payload_temperature` climbs past its configured limit and a
   `THERMAL_LIMIT` `WARNING` opens. **Power** — demand is higher by the branch's rated
   150 W. Both symptoms come from the same modelled watts, not a placed offset.
2. **Master** — press **Compare branch isolation**. On the verified run the projection was
   **15.2% no-action against 22.9% isolated**, stating that it assumes the isolator responds.
3. **Master** — approve. Measured load fell **330.7 → 179.7 W**, outcome **IMPROVED**, and
   the payload node began to cool.

Say plainly: isolation removes a load, it does not repair hardware. Release the isolator
and the fault returns.

### D04-failed — an accepted command that does not help (about 2 minutes)

**Simulator:** press **Load D04 with a failed isolator**. Identical evidence, identical
comparison, identical approval — the command is genuinely `ACCEPTED` then `APPLIED`, and
measured demand does not move. On the verified run it stayed at **329.7 W** and the outcome
reported **NO_CHANGE**, with the master console stating that recovery failed.

This is the most valuable thirty seconds of the demonstration. Most dashboards would have
shown a green tick.

### D05 — recurring scheduled overrun (about 2 minutes)

**Any console → History.** Select **Synthetic demonstration**, **Completed month**, and the
generated month.

The dataset is labelled synthetic throughout and is never mixed with live runs. It shows
**5 distinct incidents** of `ACTUATOR_MISMATCH` on `OPTIONAL_A`, one per week, 100% minute
coverage, and the commanded-versus-measured breakdown with one command missing, one
rejected, one accepted but ineffective, one outcome unknown and one improved.

Point out that a single long incident sampled for hours still counts **once** — recurrence
is counted from distinct incident records, not from samples.

If a specialist is signed in, the same window reports zero incidents and states how many
belong to other subsystems. That is the role scoping, not an empty month.

### D06 — contact loss and AI unavailable (about 2 minutes)

**Simulator:** toggle **contact loss** on during a scheduled contact window.

The app stays **CONNECTED** while the readings go **stale** — two different failures that
must look different. `DATA_STALE` opens and escalates to `CRITICAL` at 10 s. Toggle it off
and the incident resolves after the 10 s healthy dwell.

**Master:** press **Investigate stored evidence** on any incident. With no provider
configured it completes as `TEMPLATE` and says `PROVIDER_NOT_CONFIGURED` on screen, with
real citations drawn from stored evidence. The deterministic alerts, forecasts and the
recovery workflow are unaffected — that is the point.

**Never present a `TEMPLATE` result as a live model answer.** The badge is on screen; read it.

## Reset and stop

```bash
docker compose restart api
```

The backend restart brings the run back **PAUSED**; the simulator account resumes or resets
it explicitly. Stored history survives.

```bash
docker compose down
```

**Never `docker compose down -v`.** The `-v` flag deletes the `ps01_pgdata` volume and with
it every stored run, including the generated month.

## If something goes wrong

| Symptom | Cause | Action |
|---|---|---|
| Sign-in returns 403 | `APP_ORIGIN` does not match the browser's address | Fix `.env`, `docker compose up -d api` |
| A console shows stale data, app still CONNECTED | Injected contact loss, or an expected gap between passes | Expected — say so; it is a scenario, not a fault |
| A console shows DISCONNECTED | Browser or network lost the stream | It reconnects and takes a fresh snapshot; no action |
| All consoles frozen, clock stopped | Storage error — the run pauses and says so | `docker compose logs api`; the banner names the error |
| Approval returns 409 | The proposal expired, or controls moved | Compare again — this is correct behaviour |
| History shows 0 incidents | Wrong dataset, a window that is not complete, or role scoping | Check dataset and date; a specialist sees only its own subsystem |

**Offline fallback.** The whole stack is local: Caddy, the API and PostgreSQL run in
Docker on one laptop with no external dependency. If venue connectivity fails, serve the
other four laptops from that machine over the LAN — set `APP_ORIGIN` and `SITE_ADDRESS` to
that machine's address and keep `COOKIE_SECURE=false`, which is a demo-only HTTP setup and
should be described as such. Nothing in the demonstration needs the internet: AI is
disabled and the historical month is generated locally.

If even that fails, the honest fallback is to present the recorded evidence in
`docs/validation.md` and say plainly that the live stack is unavailable. Do not present
recorded results as live.

## What was verified on the deployed stack

Recorded so nobody has to re-derive it. Full tables in `docs/validation.md`.

- The Compose stack builds and runs: `ps01-api` image, Caddy, PostgreSQL. The API applies
  its migrations at start and runs one Uvicorn worker.
- Caddy serves the export and proxies `/api`. A direct refresh of `/master/` returns 200,
  not a 404; an unauthenticated `/api/incidents` returns 401.
- **SSE is not buffered by the proxy.** Two concurrent clients received identical frames
  with inter-arrival gaps of 0.98–1.11 s and none under 0.2 s, so `flush_interval -1` is
  doing its job.
- The session cookie is `HttpOnly` and the CSRF cookie is readable, through Caddy.
- `docker compose restart api` brings the run back **PAUSED**, with the same run id.
- `docker compose down` (without `-v`) preserved 7,938 stored frames and 13 runs.
- Over the LAN address, the static site and `/api/health` answer, but login returns **403**
  until `APP_ORIGIN` is set to that address. That is the LAN fallback step above, and it
  was confirmed by observing the 403.
